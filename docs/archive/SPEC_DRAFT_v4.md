# Tag-Based Artifact Discovery — Specification

**Date:** 2026-05-11
**Status:** Draft v4 for independent design review
**Supersedes:** SPEC_DRAFT_v3.md (retracted)
**Built from:** END_TO_END_MAP.md (`21cf558`) — the ground-truth map that surfaced v3's inverted dependency.

This document specifies the corrected architecture for the museum's tag-based artifact discovery feature. v3 inverted the dependency between MediaVault and the museum: it had the museum displaying authored card content with MV contributing tag overlays, when the operator's intent was the reverse — MV holds artifacts, the museum displays them.

v4 inverts the dependency back. The end-to-end map at `21cf558` is the source of every decision in this document.

This v4 is also a renaming. "Deep Dive" was an internal label that escaped into the architecture and got reified as `deep:*` namespace prefixes, special save handlers, separate UI tabs, and distinct render paths. The operator's correction — "all tags are equal" — retires the label. The feature is, plainly, **tag-based artifact discovery**. Tags are tags. Artifacts are artifacts. The visitor filters one with the other.

---

## 1. What the feature is

The museum's HR exhibit deck displays released MV artifacts. Each artifact carries a flat array of tags. The deck offers pill columns — one per tag group — and a search input. The visitor clicks pills (or types in the search) to narrow the displayed artifacts.

That is the whole feature.

### Five-step operator workflow

1. **Operator prepares an artifact in MediaVault.** Adds a YouTube video (or other source). Attaches tags from any group in the vocabulary.
2. **Operator releases the artifact in MediaVault.** Status becomes `released`.
3. **Operator runs an export** from their laptop. The export pulls released HR artifacts from MV and writes them to `src/data/hr-artifacts.json` in the museum repo.
4. **Operator commits the JSON, builds the museum, deploys.**
5. **Visitor opens the museum.** Sees the released artifacts. Filters by tag pills. The displayed set narrows.

### What the visitor sees

A grid of artifact tiles. Each tile shows what the artifact is — title, date, source link, possibly an embedded preview. Above the grid, three tiers of pill columns. Visitor clicks pills; matching artifacts surface, non-matching artifacts vanish. Same `matchFilter` mechanism the existing deck uses, generalized over a vocabulary-driven set of dimensions.

## 2. Architectural decisions

### Decisions that survive from v3

These are unchanged because they were always correct.

| Decision | Value |
|---|---|
| Vocabulary file | `docs/deep-dive-vocabulary.csv` — flat CSV, three columns (`tag`, `group`, `notes`). Hand-edited. Versioned in git. (Filename retained for now to preserve git history; may be renamed in a later commit.) |
| Vocabulary derived JSON | `src/data/deep-dive-vocabulary.json` — generated by prebuild script from the CSV. Statically imported by the museum. |
| Export mechanism | Operator-run CLI on operator's laptop. Reads MV's `/db` endpoint. Writes a JSON file in the museum repo. Not coupled to build. Not run from CI. |
| MV reachability principle | Build-time reads from the museum repo are fine. Build-time reads from MV are forbidden. |
| Filter scope | `status='released' AND scope:hunter_root` + youtube parents. Same SQL filter as v3 with `archived_at IS NULL` added. |
| Card identity migration (`c14267e`) | Stays in git history. Not relied on for this feature, but useful for unrelated future work that needs to identify authored content individually. |

### Decisions that change

These are where v3 was wrong and v4 corrects.

| Concept | v3 had | v4 has |
|---|---|---|
| Source of displayed content | Authored card files (`hr_artifacts.js`, etc.) | Released MV artifacts |
| Join mechanism | `card_id:` token in MV's `notes` | None — MV artifact id is the only identity |
| Tag namespace | `deep:<group>:<tag>` prefix for Deep Dive tags only | Plain `<group>:<tag>` — same shape as existing namespaces (`scope:`, `platform:`, etc.) |
| MV curation surface | Separate Deep Dive tab with its own save handler | Standard MV pill curation. No special tab. |
| Museum deck data source | `HR_CARDS` (composed from authored files) | Exported artifact records (consumed from JSON) |
| Export output keying | Card id (`art-014`) → group → tags | MV artifact id (`MV-20260510-001`) → full artifact record |
| `attachDeepTags` adapter | Joins tag arrays onto cards by `card_id` | Removed. Artifacts are the records; tags are on them directly. |

## 3. Architecture

### 3.1 Storage

**MV-side** — same as today, no changes:
- `artifacts` table holds rows.
- `artifacts.tags` is a JSON array of `<namespace>:<value>` strings.
- The vocabulary CSV's groups become first-class namespaces: `mood`, `theme`, `motif`, `texture`, alongside existing `scope`, `platform`, `content_kind`, `author`, `era`.
- Example tag on a released artifact: `["scope:hunter_root", "platform:youtube", "content_kind:official", "author:hunter_root", "mood:snarky", "motif:pink-hats"]`
- No `deep:` prefix. No special namespace for vocabulary-CSV-driven tags.

**Museum-side**:
- `docs/deep-dive-vocabulary.csv` — vocabulary, hand-edited.
- `src/data/deep-dive-vocabulary.json` — derived, prebuild-generated.
- `src/data/hr-artifacts.json` — generated by export. The full list of released artifact records the museum displays.

### 3.2 Data flow — operator curation

1. Operator pastes a YouTube URL (or uses `yt-ingest.mjs` CLI).
2. Standard MV pill curation. Operator clicks pills across all groups: existing groups (era, content_kind, etc.) and vocabulary groups (mood, theme, motif, texture). All tags go into `artifacts.tags` the same way. **No special tab. No card_id field. No notes storage convention.**
3. Operator clicks Release. Status becomes `released`.

That's it. MV has no concept of museum cards. MV doesn't read the vocabulary CSV at curation time (the vocabulary CSV is the museum's authority, and the operator's pill choices in MV are already constrained by MV's existing pill wall — which can be informed by the CSV, but doesn't have to be).

(Open question — see §4 Q-1: should MV's pill wall surface vocabulary-CSV tags as suggestions? Probably yes for operator efficiency. But this is curation UX, not architecture.)

### 3.3 Data flow — export

`npm run export-deep-tags` (existing command name retained for now; may be renamed to `export-artifacts` in a later commit).

The script:

1. Reads the vocabulary JSON to learn which groups exist.
2. Fetches `GET http://127.0.0.1:51822/db` from MV.
3. Loads into `better-sqlite3`.
4. Runs SQL:
```sql
   SELECT a.id, a.source_url, a.source_platform, a.media_type,
          a.tags, a.description_short, a.description_long,
          a.post_date, a.post_date_confidence,
          a.released_at, a.thumbnail_path,
          a.parent_artifact_id
   FROM artifacts a
   WHERE a.status = 'released'
     AND a.archived_at IS NULL
     AND a.parent_artifact_id IS NULL
     AND a.source_platform = 'youtube'
     AND EXISTS (
       SELECT 1 FROM json_each(a.tags)
       WHERE json_each.value = 'scope:hunter_root'
     );
```
5. For each row:
   - Parses `tags` JSON array as a flat list of strings.
   - Splits each tag on first colon: `"mood:snarky"` → `{namespace: "mood", value: "snarky"}`.
   - Groups tags by namespace.
   - Validates against vocabulary JSON: tags in declared groups (mood, theme, motif, texture) are first-class; tags in undeclared namespaces (scope, platform, etc.) pass through as filter-only metadata.
6. Writes `src/data/hr-artifacts.json`:
```json
   {
     "metadata": {
       "exported_at": "2026-05-11T...",
       "filter": "released, scope:hunter_root, youtube parents",
       "vocabulary_csv_sha": "<12-char sha>"
     },
     "artifacts": [
       {
         "id": "MV-20260510-001",
         "source_url": "https://www.youtube.com/watch?v=7Lttb_59EYw",
         "source_platform": "youtube",
         "media_type": "link",
         "title": "Reverend",
         "description": "Hunter Root - Reverend (official music video)",
         "post_date": "2023-03-30",
         "released_at": "2026-05-11T...",
         "thumbnail_url": "https://i.ytimg.com/vi/7Lttb_59EYw/maxresdefault.jpg",
         "tags": {
           "scope": ["hunter_root"],
           "platform": ["youtube"],
           "content_kind": ["official"],
           "author": ["hunter_root"],
           "mood": ["snarky"],
           "motif": ["pink-hats"]
         }
       }
     ]
   }
```

(Note: `description_short` and `description_long` may be combined into a single `description` field; the export decides the rendering-friendly shape. Similarly the thumbnail URL is derived from the artifact's children — the second-row child whose `media_type='photo'`. This requires a small lookup but is straightforward.)

### 3.4 Data flow — museum render

1. At build time, Vite imports `src/data/hr-artifacts.json` (existing static-import pattern).
2. The prebuild step regenerates `deep-dive-vocabulary.json` from the CSV.
3. `HR_DIMENSIONS` is built dynamically from the vocabulary JSON's `groupOrder`. One dimension per group. Plus any other existing dimensions (era, content_kind, platform) backed by the artifact records' tag arrays. **(All dimensions come from artifact records' tags; no separate static dimension definitions.)**
4. The deck (`HrExhibitFlow.jsx`) renders the artifacts array directly. Each artifact's tile shows: title (or description), date, source link with appropriate icon, thumbnail if available.
5. The deck's existing `matchFilter` is generalized: for each selected pill, check whether the artifact's `tags[<namespace>]` array contains that value.
6. The search input is the existing typeahead, scoped to vocabulary tag labels across all dimensions.

### 3.5 What's deleted

These files and code paths are no longer needed:

- `src/data/hr_artifacts.js`, `src/data/hr_archive.js`, `src/data/hr_exit_flow.js` — fake test content; deleted.
- `src/routes/hr/hr_cards.js` — adapter file that built `HR_CARDS` from the three above. Replaced by direct consumption of `hr-artifacts.json`.
- `attachDeepTags` function — no longer needed.
- `src/data/deep-tags.json` — replaced by `hr-artifacts.json`.

MV-side:

- The Deep Dive tab in `mediavault.html` — removed. Tag curation happens via the existing pill wall.
- The `card_id` text input — removed.
- `handle_artifact_deep_dive_save` endpoint — removed. The standard MV tag-save flow handles everything.
- `handle_deep_dive_vocabulary` endpoint — may be retained if MV wants to display vocabulary CSV suggestions in the standard pill wall. Otherwise removed.
- The `_parse_notes_array` / `_validate_card_id` / `_normalize_deep_pair` helpers — removed.
- The `is_proposed=1` vocabulary inserts done by the Phase 4 handler — removed. MV's standard vocabulary management remains.

## 4. Open implementation questions

### Q-1 — Should MV's pill wall surface vocabulary-CSV tags as suggestions?

MV's standard pill wall reads tag suggestions from MV's `tags` table (per `SPEC.md §2.5`). The vocabulary CSV is a separate suggestion source maintained in the museum repo.

Options:

- **(a) MV reads the vocabulary CSV** at the hardcoded path (same as Phase 4 did) and merges those tags into the pill wall as additional suggestions.
- **(b) MV does not read the CSV.** The operator must add vocabulary tags to MV's `tags` table separately (via Vocab Admin or `/api/tags`).
- **(c) A small one-time sync script** reads the CSV and inserts its tags into MV's `tags` table on demand.

Recommendation: **(a)**. It preserves the cross-repo binding from Phase 4 (which was the one thing v3 got right architecturally) without coupling MV to the museum's render layer. The pill wall just gets more suggestions; the operator picks what to use.

This is `[locked: Ops]` pending operator confirmation.

### Q-2 — Should `description_short` and `description_long` be a single field in the export?

`description_short` is typically the YouTube title; `description_long` is operator-authored or the YouTube description. The deck needs one renderable field per artifact.

Options:

- **(a) Combine in the export** — single `description` field, preferring `description_short`.
- **(b) Export both** — let the museum decide.
- **(c) Add a `title` and `description` field separately** — `title = description_short`, `description = description_long`.

Recommendation: **(c)**. Standard separation. Museum renders title prominently and description in a hover or expand state.

### Q-3 — How does the deck render artifacts of media_type `'photo'` or `'text'`?

Today's data has YouTube videos as `media_type='link'` parents, but MV supports other media types. Should the export filter to `media_type='link'` only, or should the museum render whatever comes?

Recommendation: export everything that matches the SQL filter; the museum has a render dispatch on `media_type` that handles each shape. Phase 1 of build only needs `link`; other media types can render as placeholders until their renderers are built.

### Q-4 — What is the relationship between Phase 0.5's card-identity migration and this architecture?

Phase 0.5 added `id` fields to entries in `hr_artifacts.js` / `hr_archive.js` / `hr_exit_flow.js`. Those files are now deleted. The migration's value to this feature: zero.

The migration's value in general: still positive for any future feature that adds authored content alongside released artifacts. The migration stays in git history. The files it migrated do not.

## 5. Two implementation paths

The map established that the current code is foundationally wrong. v4 specifies the correct architecture. There are two reasonable ways to get from current state to v4-compliant code.

### Path A — Burn It Down

Revert `main` of both repos to pre-feature state. Build forward from a clean slate to match v4.

Reverts on museum repo (in reverse order): `21cf558` map (keep), `53394ff` playbook (keep), `caf1b01` gitattributes (keep), `8872ec0` export fix (revert), `860ee05` Phase 3 export (revert), `bb2c343` Phase 1 wiring (revert).

Reverts on MV: `d52e3ef` Phase 4 (revert).

Keeps: all verification reports, decision history, v2 spec, v2 review, v3 spec, v3 supplementary docs, end-to-end map, `.gitattributes`, `prebuild-install` patch, playbook updates. Card-identity migration `c14267e` stays (though the files it modified will be deleted in the new build).

Cost: ~6 reverts plus a fresh build to v4.

Audit trail: Sharp before/after on May 11, 2026.

### Path B — Unfuck It

Edit forward. Each existing commit gets superseded by a new commit that flips its semantics.

- Museum: new commit ripping `hr_cards.js` and the three data files, rewriting `hr_dimensions.js` to read artifacts from `hr-artifacts.json`, rewriting `HrExhibitFlow.jsx`'s data plumbing.
- Museum: new commit rewriting the export script: new SQL, new output shape, no `card_id` parse, no `deep:*` filter.
- MV: new commit ripping Phase 4's tab, ripping the `card_id` requirement, ripping the `deep:*` namespace from the save handler, leaving the vocabulary endpoint if Q-1 chooses (a).
- Renames where appropriate: `deep-tags.json` → `hr-artifacts.json`, possibly `export-deep-tags` → `export-artifacts`.

Cost: ~3-4 forward commits totaling roughly the same line count as Path A's reverts + new build.

Audit trail: Evolutionary record. Every commit message explains its transition from prior state.

### What the design review evaluates

The design review evaluates v4 (this document) for soundness against the end-to-end map. The review also evaluates each path for:

- **Execution risk**: which path is more likely to leave behind unintended residue?
- **Cognitive load**: which path makes future "what does this code do?" archaeology easier?
- **Operator-facing risk**: which path produces fewer transient broken states during execution?

Both paths reach the same end state. Choice between them is partly aesthetic (audit trail style) and partly tactical (execution discipline).

## 6. Implementation phases (v4-compliant)

Once the path is chosen, the work breaks into these phases. Phase numbering restarts to avoid confusion with v3's phases.

### Phase v4-1 — Path-specific cleanup

If Path A: execute the reverts. Confirm clean state on both repos.
If Path B: this phase is empty; phase v4-2 onward does the work.

### Phase v4-2 — Vocabulary remains authoritative

The CSV at `docs/deep-dive-vocabulary.csv` and the prebuild generating `deep-dive-vocabulary.json` are kept as-is. Possibly renamed if "deep-dive" naming is retired entirely.

### Phase v4-3 — Export rewrite

`tools/export-deep-tags.mjs` (or renamed) becomes the artifact exporter. Per §3.3.

Live test: operator releases the Reverend test artifact (`MV-20260510-001`) with tags including some vocabulary tags. Runs export. Verifies output JSON contains one entry with tag groupings.

### Phase v4-4 — Museum deck rewrite

`HrExhibitFlow.jsx` consumes `hr-artifacts.json` directly. `hr_dimensions.js` builds dimensions from the artifact records' tag arrays plus the vocabulary JSON.

Delete `hr_cards.js`, `hr_artifacts.js`, `hr_archive.js`, `hr_exit_flow.js`.

Phase 0.5's card-identity migration becomes irrelevant for this feature; commit history preserved.

### Phase v4-5 — MV cleanup

Strip Phase 4's Deep Dive tab. Strip the `card_id` field. Strip the `deep:*` namespace handler. Per Q-1's decision, retain or remove the vocabulary CSV endpoint.

### Phase v4-6 — Live end-to-end test

Operator workflow per §1's five steps. Verify a real artifact released in MV surfaces in the museum after export + build.

### Phase v4-7 — Bulk ingest

Operator-paced. The ~63 HR YouTube tracks get ingested into MV, curated, released. Periodic export. Museum displays everything.

## Appendix A — How v4 differs from v3

- **Architecture inverted.** MV is now the source of displayed content; the museum is the renderer. v3 had this backward.
- **No `card_id` concept.** The join between MV and the museum is the MV artifact id, full stop.
- **No `deep:*` namespace prefix.** Tags are tags. Vocabulary CSV groups are first-class namespaces alongside existing namespaces.
- **No special Deep Dive curation tab in MV.** Standard pill curation does everything.
- **No `hr_cards.js`, no `hr_artifacts.js`, no `hr_archive.js`, no `hr_exit_flow.js`.** Authored fake test data is deleted. The museum displays what MV has released, nothing else.
- **Export output keyed by artifact, not by card.** The output JSON is a list of artifact records, each carrying its own tags.
- **Decision provenance preserved.** v3's `[locked: ...]` tags carry forward for decisions that survived. New v4 decisions are tagged similarly.
