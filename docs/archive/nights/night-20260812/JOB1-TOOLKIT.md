`localStorage`, no textarea, no download, no fetch. It is a viewer with a
lightbox and filter chips. Anything he decides while looking at it is lost when
he closes the tab.

**That is the gap Job 4 sits in**, and it is the reason 4d matters more than 4b:
the museum has one working write-back pattern and it was built eleven days ago
for exactly this problem.

first thing offered, and its `what` says he writes in a spreadsheet
(`RECORD_days-2-to-6.xlsx`) now. The comment above it reasons the distinction

### What it gets WRONG

   write-back in the toolkit. The desk's contract is "a page opens by
   double-clicking", and `record:serve` is a *command*, so it has no card by
   construction. That is a real hole: the one instrument whose Save reaches the
   repo is the one instrument the launcher cannot offer. **It matters less this
   week because the editor is mothballed — but Job 4 wants the same pattern, and
   the same hole will apply to Job 4's page.**
2. **The desk says nothing about lint, and nothing about the baseline.** No card,
   no footer line. So the 11/9 → 9/8 move did not make the desk wrong — the desk
   has never mentioned it. Nothing to correct; worth knowing before someone
   goes looking.
3. **`tools/scroll-probe.js` is not on the desk and cannot be.** It is a
   console paste-in, not a page and not an npm script. Its own header says
   "PASTE THIS INTO THE CONSOLE". Given Mike **cannot run a `.js` file** — a
   double-click executes it instead of opening it — a bare `.js` in `tools/` is
   the wrong shape for something he is meant to use. It needs either a card that
   explains "open this in a text editor and copy it" or a wrapper that prints it
   to the terminal for selection.
4. **Six of the eight cards are three days stale** (08-09) while `record.html`
   and `OPEN_ACTIONS.html` are from last night. The desk prints each file's own
   mtime and its own rebuild command, so it reports this honestly rather than

   should know one command (`npm run dictation`) refreshes all six.
