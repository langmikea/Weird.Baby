   new size). All three commits use this `cp`-via-bash pattern. Each
   commit was syntax-checked end-to-end with `compile()` before the
   `git hash-object -w`.
2. The cosmetic `warning: unable to unlink '.git/objects/<2>/tmp_obj_*'`

### 5.4 Cowork-on-Windows mount: file-write truncation pattern

A new variant of the Phase 1 §5.4 mount artifact: file Writes /
Edits that grow a file past its original byte length silently
truncate the on-disk file at the original size. The host-side Read
tool sees the full new content (it shares the same Edit-tool
buffer); the Linux mount sees the truncation.

Verified empirically: each Phase 2.1 Edit succeeded ("file updated
successfully"); subsequent bash inspection showed
`core/imgserver.py` at exactly 68059 bytes (original size) with the
end mid-line at `"/ext/hr_manager_rende` (truncated). The file's
SHA differed from HEAD's (so the bytes WERE written) but the size
was clamped.

Workaround: write the corrected file to `/tmp/...` via Python
heredoc; `cp /tmp/file core/file`. The bash-side `cp` overrides the
mount's clamp and the file lands at its real new size. All three
Phase 2A commits use this `cp`-via-bash pattern for any growth.

The `git hash-object -w` /
`git update-index --cacheinfo` / `git commit-tree` chain proceeds
normally after that — same plumbing path as Phase 1 §5.4. The
`warning: unable to unlink '.git/objects/<2>/tmp_obj_*'` messages
are cosmetic noise; the canonical SHA file is created at the same
time.
