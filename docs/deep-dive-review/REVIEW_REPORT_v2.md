# Design review — Deep Dive spec v2
**Date:** 2026-05-10
**Reviewer:** Fresh Claude conversation, adversarial read-only review
**Source material:** Phase 0 audit, Status taxonomy research, Decision history, Spec draft v2

This is the report produced by an adversarial design review conducted on the v2 spec. v3 was drafted in response to this report. The report is preserved here for the audit trail showing what drove v3's revisions.

## Drift findings

**§3.4 step 4 — export query construction.** The spec writes the SQL as `tags LIKE '%"scope:hunter_root"%'`. D7's locked filter, as quoted in the decision history and in the spec's own §2 table, is `tags @> 'scope:hunter_root'`. These are not the same operation. `LIKE '%"scope:hunter_root"%'` is a substring match on the JSON-serialized text (and depends on the exact quoting), while `@> 'scope:hunter_root'` is a JSON-array containment check. The spec presents the `LIKE` as the implementation of the locked filter without acknowledging it has substituted one for the other. This is drift from the locked decision text, not a deliberate divergence.

**§4 — characterization of the status enum drift as something the export "depends on."** The Status research Finding 9 quote is: "Code, schema, and spec all give different answers to 'what can status be?'" The research describes this as a documented inconsistency deferred to v0.7. The spec elevates this to "a real defect that the export depends on" and constructs a fragility argument ("if MV ever produces a row with the wrong status value... behavior is undefined"). The source material does not characterize the drift as a defect the export depends on; it characterizes it as a bookkeeping inconsistency. The spec's framing escalates the source's framing, which then motivates the Phase 2 recommendation in §6.

**§3.4 step 6 — `source_url` parsing for `ytId`.** The spec asserts that the export script will "parse `source_url` to extract the YouTube `ytId` (the museum's primary key)." Phase 0 does not document a `source_url` column on `artifacts`, does not establish that YouTube `ytId` is the museum's primary key for video artifacts, and does not establish that this parse is reliable. The yt-ingest CLI is mentioned in Phase 0 Q4 as a developer-side tool that POSTs to `/api/artifact-register`, but its output schema is not described in the audit. The spec is asserting a data shape and a join key that the source material does not establish.

## Silent assumptions

**The `deep:` namespace prefix exists in the existing pill convention.** §2 derived decisions and §3.6 both claim that `deep:` matches "the existing pill convention (`scope:`, `platform:`, `content_kind:`, `artifact_kind:`, `author:`, `era:`)." Phase 0 Q3 mentions a `bands:hunter_root` convention from SPEC.md §2.1/§2.2 and the Status research mentions `scope:hunter_root` as actually-shipped. Neither source material document enumerates the full list of prefixes the spec cites (`platform:`, `content_kind:`, `artifact_kind:`, `author:`, `era:`). The reader cannot tell from the source whether the spec author confirmed these prefixes exist or assumed them by analogy. Resolution: cite where each named prefix is established.

**The CSV is parseable at build time without new dependencies.** §3.5 step 2 says the vocabulary CSV is "parsed at build time (either via a Vite loader or a small `prebuild` step that converts CSV → JSON; resolved in Phase 1)." Phase 0 Q5 explicitly notes there is no `prebuild` script today and `vite.config.js` has no custom data-loading plugin. Adding either is a non-trivial decision the spec defers without acknowledging it cuts against the "operator-CLI, not build-coupled" principle the spec asserts elsewhere. The reader cannot tell whether the spec author considered that a `prebuild` step here re-introduces the build coupling that §2's derived decision rejected for MV. Resolution: state explicitly whether the CSV→JSON conversion is build-coupled or operator-CLI.

**`HR_CARDS` carries a `deep` field per card.** §3.5 step 6 says "the card-side data... needs a `deep` field per card carrying the array of tags for that video. **This is where the museum's existing data files meet the export.** Resolved in Phase 1." The audit (Phase 0 Q2) documented that adding a column requires cards to carry that field "(string for `single`, array for `multi`) using the same slug grammar; otherwise every pill in the new column reads zero-count and renders un-clickable." The spec asserts the data will be there but does not address the question of *how* `deep-tags.json` (keyed by `ytId`) joins to `HR_CARDS` (which the audit did not establish is keyed by `ytId`). The source material does not establish the join. Resolution: identify the join key in `HR_CARDS` and confirm it matches `ytId`, or state that this is unresolved.

**Free-form tags become Deep Dive tags via `is_proposed=1`.** D3 in the spec table says "novel free-form tags persist as `is_proposed=1` in MV." Phase 0 Q3 documents that `/api/tags?proposed_only=1` exists and that the `is_proposed` column is real. Status research §10 and Phase 0 Q3 both note SPEC v0.5 declares `is_proposed` retired with a one-stage vocabulary, although the column persists. The spec assumes `is_proposed` is the right hook, but the source material flags it as a column the spec system has retired conceptually. Resolution: state whether the spec is committing to keep `is_proposed` alive (against SPEC v0.5's direction) or whether some other mechanism is intended.

**The export filter as expressed survives the status enum drift.** §4 says "the export script in this spec depends on `status = 'released'` which all three layers agree exists — so technically the export works today against the drift." The Status research Finding 9 quote is that the runtime `STATUS_ENUM` "Contains `deleted` (DB would reject it), omits `inbox` (DB would accept it)." The spec's claim that all three layers agree on `released` is correct as far as it goes, but the silent assumption is that the *only* way the drift could affect the export is via the `status` value itself. The reader cannot tell whether the spec author considered other failure modes (e.g., a row with `archived` as status — which the schema accepts and the runtime accepts but SPEC retired — that should perhaps be excluded from export but isn't filtered by `archived_at IS NULL` because `archived` is a status value, not a column flag).

## Coverage gaps

**`hr_facts.js` as a search target — actually addressed, but the spec misrepresents the source.** D6's "Audit basis" cell cites "Phase 0 Q1 + Constraints §7. The deck and `Exhibit.jsx` consume different data slices; bridging them is non-trivial." Phase 0 Constraint #7 says only that the audit "couldn't tell from the code whether Deep Dive is intended to search fact text" and asks the spec to specify. It does not say bridging is non-trivial. The spec is treating its own §7-deferral rationale as if it came from the audit. (This belongs more in "decisions picked rather than made" but is also a coverage issue: the audit's actual question — what is the search scope — was answered, but the rationale for the answer is invented.)

**`/api/queue` and `/api/fb-candidates` endpoints.** Phase 0 Q3 enumerates them as read endpoints with implications for an export. The spec does not address whether they're relevant to Deep Dive. The Audit findings utilization map (Appendix A) does not list them. The silence may be correct (they probably aren't relevant) but the spec doesn't say so.

**`/ping` endpoint.** Phase 0 Q3 lists `/ping` as a health check. The export CLI in §3.4 makes one HTTP request to `/db` with no precondition check. The audit doesn't require a precondition check, but the spec also doesn't address what happens when MV is not running on the operator's laptop at export time (connection refused, no JSON written, exit code, etc.). The audit's Constraint #5 (loopback-only MV) implies this failure mode is real and frequent.

**Asset bytes for video posters/thumbnails.** Phase 0 Constraint #6 says: "If Deep Dive needs to render images, the spec should include asset-delivery (R2? bundled? linked back to localhost MV in dev only?) explicitly." The spec defers this in §7 with the trigger condition "if a future surface needs MV-derived images" — but the deck *today* renders cards that include images (Phase 0 Q2 documents `HR_ARTIFACTS`, `HR_ARCHIVE`, `HR_EXIT_FLOW` as the data sources, which carry image references). The spec does not establish whether the new `deep`-column-filtered cards inherit the existing image pipeline unchanged or whether new MV-sourced artifacts that surface only via Deep Dive need image bytes. The silence matters because Phase 5 says "Mike pastes one new YouTube URL... verifies the new tags appear in the search, filter the deck correctly" — but that requires the new artifact to render as a card, which requires whatever image pipeline `HR_CARDS` uses.

**`/api/tags` — actively rejected in the utilization map without rationale that holds up.** Appendix A says `/api/tags` was "rejected because we don't need full tag rows, just the artifact-to-tag mapping. `/db` carries that." Phase 0 Q3 documents that `/api/tags` is the canonical surface for tag vocabulary including the `is_proposed` filter. The vocabulary CSV in this spec is a *separate* vocabulary from MV's `tags` table — but D3 says novel free-form tags "persist as `is_proposed=1` in MV" and Phase 4 surfaces a curation UI that "reads the vocabulary CSV." The spec does not address how MV's `tags` table (which holds the `deep:*` tags that artifacts actually reference) relates to the CSV. Are they two separate vocabularies that must be kept in sync? Is the CSV authoritative and `tags` derived? Is `tags` authoritative and the CSV a snapshot? The source material doesn't answer this; the spec doesn't either.

**The audit's "Deep Tracks search overlap with the Deep Dive feature" constraint.** Phase 0 Constraint #1 was "Mike should confirm whether Deep Dive is an extension/replacement of the Deep Tracks search." The decision history records Mike's answer (D1). The spec captures D1 but does not address the audit's specific worry about "migration / coexistence of the existing input." The spec implicitly answers this (it's the same input, no migration) but does not say so explicitly.

## Decisions that look picked-rather-than-made

**D2 — flat with group-as-column.** The decision history records that Mike's first answer was "b" (grouped, light, *with category prefixes* like `mood:snarky`). His elaboration ("easy to edit in a table... I select these tags, change their 'group' labels to 'Oops'...") was treated by the Ops author as a refinement that ruled out prefixes and pointed toward a flat table with a group column. This is a real reinterpretation. The first answer endorsed prefixes; the second answer was about renamability. The Ops author resolved the tension by treating renamability as primary and prefixes as incompatible with renamability. That resolution may be sound but it is the spec author's resolution, not Mike's. The spec records D2 as "Flat. Storage is one row per tag" without acknowledging that the "flat" framing supplants the "b" the operator initially picked. Notably, the spec then *uses prefixes anyway* (the `deep:` namespace prefix in `artifacts.tags[]`) — the prefixes were ruled out at the *vocabulary* layer but reintroduced at the *storage* layer. The decision history doesn't establish that Mike consented to that split.

**D6 — "Simplify, please" → tags only.** The decision history flags this explicitly: "Treating 'simplify' as a vote for (a)." The spec records D6 as locked with the value "Tags only." "Simplify" is an instruction, not a choice; the Ops author chose (a) on Mike's behalf. The decision history asks the reviewer to test whether this should have been picked back to the operator. The spec presents D6 as locked.

**D7 — `archived_at IS NULL` clause.** The decision history notes: "the `archived_at IS NULL` clause was not in the option (c) text but was added in the spec." Mike said "I agree" to option (c) which was written as "Released + tag-scope (e.g., `released AND tags @> 'scope:hunter_root'`)." The `archived_at IS NULL` predicate was not in what Mike agreed to. The spec presents the full three-clause filter as locked. D8 ("Archive removes the artifact from the museum") supplies the underlying intent and is itself an "I agree" to a recommendation, so the clause is consistent with the spirit, but the predicate itself was not in the option Mike endorsed.

**D8 — same "I agree" pattern.** The decision history asks: "Were these genuine endorsements or compliance? The operator was answering rapidly at that point." The spec presents D8 as locked. The reviewer cannot tell from the source material whether the spec author tested for compliance or assumed endorsement.

**The four "architectural decisions made by the Ops author after the eight."** The decision history names these explicitly as "Operator confirmation: None explicit" for the vocabulary file location, the per-video tag storage location and `deep:` namespace, and the export mechanism details. The spec presents these in §2 as "Two derived architectural decisions (also locked, but not numbered above)" and in §3 as part of the architecture. The decision history's framing — "**Reviewer should test these**" — is at odds with the spec's framing as locked.

**Q-A's "recommendation" frames a decision as already-made.** §5 Q-A asks "is this drift acceptable, or should the spec correct it now" but the spec has *already* used `scope:hunter_root` in D7's filter and elsewhere. The question is presented as open but the spec has committed. If Mike answers "rename it," D7's filter must change. The spec does not flag that Q-A's outcome can invalidate D7.

## Internal consistency issues

**§2 says the export is "build-time export... Not a Vite plugin, not a `prebuild` hook." §3.5 step 2 says the vocabulary CSV is parsed at build time "either via a Vite loader or a small `prebuild` step that converts CSV → JSON; resolved in Phase 1".** The spec rules out build-coupling for the MV→museum path on principled grounds (loopback-only MV, deliberate-export framing) and then introduces build-coupling for the CSV→museum path. These may be reconcilable (the CSV is in the museum repo, no loopback issue) but the spec asserts the principle in one place and contradicts it in another without acknowledgment.

**§2 derived decisions list "Two derived architectural decisions (also locked, but not numbered above)" but then enumerates three bullets** (vocabulary file location, per-video tag storage, MV→museum transfer). Cosmetic, but signals editorial drift.

**D7's filter expression is written two different ways.** §2 table: `status = 'released' AND archived_at IS NULL AND tags @> 'scope:hunter_root'`. §3.4 step 4: `SELECT * FROM artifacts WHERE status = 'released' AND archived_at IS NULL AND tags LIKE '%"scope:hunter_root"%'`. These are not equivalent operations (see Drift findings above). The metadata block in §3.4 step 7 reverts to the `@>` form, so the JSON written to disk says one thing while the query that produced it did another.

**§6 Phase 2 is described as "contingent on Q-B answer"** but §4's "Recommendation" already strongly endorses Phase 2 as in. §6 also lists Phase 2 as "**Prerequisite to Phase 3**" in bold. If Mike answers Q-B with "out," Phase 3 has no prerequisite; if "in," Phase 2 is a prerequisite. The spec presents the prerequisite as if Phase 2 is decided.

**§3.3 says "Tags already assigned to artifacts in MV remain on those artifacts even if removed from the vocabulary CSV."** §3.4 step 5 says the export extracts all `deep:*` tags from artifacts. The export does not filter against the CSV. So a tag that was once in the CSV, then removed, will still flow to the museum on every export — meaning the museum's deck will display a pill for a tag that no longer exists in the vocabulary. The spec does not address this. (This may be the intended behavior — "describe what is suggested during curation, not what is valid at storage time" — but the consequence at the museum surface is not addressed.)

## Out of scope (impulses I had but did not act on)

- I wanted to suggest that the export script should validate `deep:*` tags on artifacts against the current CSV and either warn or filter. (See last item in Internal consistency.)
- I wanted to suggest that Phase 5 should include a regression test against the search-pill-rendering behavior with an empty `deep` column.
- I wanted to suggest that the spec should specify the join key between `deep-tags.json` and `HR_CARDS` rather than deferring to Phase 1.
- I wanted to redesign the `tags @>` vs `LIKE` resolution by suggesting a JSON-aware SQLite extension or `json_each`. Not my job.
- I wanted to suggest that Q-A's resolution should be hoisted out of "open questions" and into a locked decision before the spec is signed off, since it can invalidate D7.

## Bottom line

The spec needs five specific corrections (listed above). It is not fundamentally drifting — the architecture is sound, the audit findings utilization is genuinely thorough, and the v2 rewrite has corrected the v1 draft-from-priors pattern at the structural level. But the spec retains the same pattern in subtler form: it presents synthesized decisions as locked, substitutes its own framings for source material framings, and introduces implementation details (the `LIKE` query, `source_url` parsing, the `deep:` prefix list, the build-time CSV parser) that the source material does not establish.

In priority order:

1. **The D7 filter is written two different ways** (§2 table vs §3.4 step 4) and the implementation form (`LIKE`) is not equivalent to the locked form (`@>`). This is the highest-priority correction because the export query is load-bearing and the spec is internally inconsistent about what it is.
2. **D2's reinterpretation, D6's "simplify," and D7/D8's "I agree" responses are presented as locked operator decisions** when the decision history explicitly flags them for reviewer scrutiny. Either re-confirm with Mike or mark them as Ops-author-resolved with the operator's tacit acceptance.
3. **The four post-eight architectural decisions** (vocabulary location, `deep:` namespace, export mechanism, and Phase 2 cleanup) are presented as locked but the decision history records "Operator confirmation: None explicit" for the first three and "NOT YET CONFIRMED" for the fourth. Either get explicit confirmation or restyle as recommendations.
4. **The `source_url` → `ytId` parse and the `HR_CARDS` join key** are asserted but not grounded in the audit. The spec needs to either cite the audit on these or surface them as Q-G/Q-H.
5. **The CSV→JSON build-time parse contradicts the "no build coupling" principle** asserted in §2. The spec needs to either reconcile (the principle is about MV specifically, not all build-time data) or pick a different mechanism.
