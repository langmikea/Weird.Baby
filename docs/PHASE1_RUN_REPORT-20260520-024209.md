### 5.4 Cowork-on-Windows mount: `unlink` is blocked, `rename` works

A repeating pattern this session: the Linux sandbox can stat files in
the mounted Museum tree, can rename them within the same directory,
can create new files, can write to existing files — but **cannot
unlink files** in directories owned by Windows. `rm` and `mv`-to-different-dir
return `Operation not permitted`; `mv`-within-same-dir succeeds.

This forced two workarounds:

1. **Git index/refs.** `git add`, `git commit`, and `git write-tree`
   acquire `.git/index.lock` and `.git/refs/heads/main.lock` via
   create-then-unlink semantics. The unlink step fails (and stale
   `.lock` files become invisible to `ls -la` of the parent dir but
   visible to git's `O_CREAT|O_EXCL`, blocking subsequent operations).
   Workaround: build the index under `/tmp/idx_*` (writable normally),
   use `GIT_INDEX_FILE` to redirect git plumbing at it, use direct
   `mv` and `echo > refs/heads/main` to advance the branch. All three
   Phase 1 commits use this path. No object integrity issue — the
   warnings about `unable to unlink '.git/objects/<2>/tmp_obj_*'` are
   cosmetic (the canonical SHA file is created at the same time;
   verified by re-`hash-object -w` returning the same SHA).

2. **Working-tree file removal in 1.4.** `tools/build-deep-tags-vocabulary.mjs`,
   `src/data/deep-dive-vocabulary.json`, and
   `docs/deep-dive-vocabulary.csv` were removed from the tree object
   (`git update-index --force-remove`) but could not be `rm`'d from
   the working tree. They were moved to
   `.phase1_retired_files/` (a sandbox-local rename) so they don't
   show as untracked next to the committed deletion. The operator can
   `rmdir /s .phase1_retired_files` (or `Remove-Item -Recurse`) on
   Windows to actually delete them. Not blocking — they're not
   tracked.

This isn't a Phase 1 bug; it's a Cowork environment artifact and the
same pattern Criterion 7 hit with `dist/` (its report §"What ran"
noted the same EPERM on `dist/weird_baby/.vite/manifest.json`).
