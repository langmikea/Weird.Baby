**Date:** 2026-06-01
**Author:** Cowork diagnostic session (read-only — measure + report, no build)
**Status:** DIAGNOSTIC ONLY. No build, no edit, no deploy, no commit. Findings doc for operator commit.
**Site measured:** Live `https://weird.baby/hr`, in the operator's connected Chrome ("Chonger", logged-in).
**Viewport:** 1920 × 869. Grid: `.hr-artifact-grid`, 64 `.hr-card` tiles.
**Source cross-referenced:** `src/routes/hr/HrExhibitFlow.jsx`, `src/routes/hr/HrExhibitFlow.css` (host-intact via Read tool).

---

## 0. Bottom line up front

The grid renders **64 cards**. By shape:

| Class | Count | What it means |
|---|---:|---|
| ✅ clean | 29 | Content fills its tile; aspect correct; no material empty gutter |
| ⚠️ mis-shaped | 18 | Content renders, but the tile is stretched well past it → large empty gutter below the foot |
| ❌ broken | 17 | Tile shows **nothing** (16 empty Facebook boxes) or is **collapsed** (1 album sliver) |

Three root causes account for everything. Two are small, surgical fixes (one CSS line; one width-hook/​fallback fix). The third — ragged heights / gutters — is structural: a **row-based** CSS grid is being asked to lay out cards whose heights vary 5× by design, and a row grid converts that intended variety into empty gutters. The variety itself (random column spans, per-type aspect ratios) is **operator-locked and correct-by-design**; the gutter is the defect.

The single biggest visible problem is the **16 Facebook cards rendering as empty boxes** — and that is **not** the logged-out caveat. It reproduces in the operator's own logged-in browser because the embed iframe never mounts at all (upstream of Facebook auth). Nobody — operator or public — currently sees Facebook content in the grid.

## 1. How the grid sizes a card (the mechanism)

Confirmed from source + live computed styles:

- **Grid:** `.hr-artifact-grid { display:grid; grid-template-columns: repeat(4, minmax(0,280px)); grid-auto-rows:auto; gap:14px; grid-auto-flow:dense; justify-content:start; }` (CSS L133–140). Grid items inherit the default `align-items: stretch`.
- **Column span (width):** `pickSpan(id)` (JSX L841–850) is a deterministic FNV-hash of each artifact id → an effectively random 1-or-2-column span. Link/YouTube cards are biased 70% wide (span 2); other types 20% wide. **This is the operator-locked "B rule" (2026-05-22): "same shape per type, varying sizes via column-span."** Span 1 = 280px tile, span 2 = 574px tile.
- **Height:** comes from a per-type `aspect-ratio` on the inner `.hr-card-video-vis` box (CSS L163–165, L240–242, L1189), times the computed width. So a span-2 card is automatically ~2× taller than a span-1 card of the same type. Aspect ratios in play: `link/youtube 16/9`, `photo 4/5`, `audio 1/1`, `fb-video 16/9`, `fb-post 4/5`, `fb-reel 9/16`, `gallery 4/5`.
- **Row height:** because rows are `auto` and items `stretch`, **each grid row's height is set by its tallest member**, and every shorter card in that row is stretched to match — its `.hr-card-video-vis` stays fixed (`flex:none` + aspect-ratio), so the extra height becomes **empty card background below the foot**. This is the gutter.

Live grid row tracks (px), in order, show the raggedness directly:
`416, 416, 442, 442, 442, 785, 375, 588, 400×16, 768, 55`
— most rows ~400, but a 785 row (driven by the Instagram photo), a 588 and 768 row (driven by reels / the gallery cover), and a final 55px sliver row (the collapsed album).

## 2. Root-cause groups

### RC-A — Facebook inline embeds never mount → 16 empty boxes ❌ (highest impact)

**Symptom:** all 16 `.hr-card-fbembed` tiles render an **empty** `.hr-card-video-vis` (verified: 0 `<iframe>`, 0 `<img>`, no background-image, 0 child nodes — after fully scrolling the real scroll container `.wb-scroll.hr-panel-scroll`, so this is not a lazy-load artifact). The box still has a per-kind shape from CSS (16/9 video, 4/5 post, 9/16 reel), so it occupies space but shows nothing but a white rectangle + the foot (title, date, "Open on Facebook ↗", ⤢ expand).

**Mechanism (pinned to source):** In `FbEmbedCard` the iframe is gated `{embed && tileW > 0 && (<iframe…/>)}` (JSX L1699). `tileW = visW` comes from `useElementWidth()` (JSX L1148–1164), whose `ResizeObserver` callback only calls `setWidth(w)` `if (w)` — it discards a 0-width initial reading and, in the deck's mount sequence, never receives a later non-zero callback. So `tileW` stays **0**, the gate is false, and **no Facebook card ever mounts its iframe**. Corroboration: every FB `.hr-card-video-vis` has **no inline `style` attribute** at all, meaning both inline branches in `FbEmbedCard` (`if (dims)` and `else if (tileW>0)`) were skipped → `tileW===0` confirmed live. There is also **no static thumbnail fallback**, so a non-mounting embed degrades to a blank box rather than an image.

**Not the logged-out caveat.** Because the failure is upstream of Facebook (the frame is never created), it is identical for the logged-in operator and a public visitor. The scoping doc's "logged-out ≠ operator view" risk is real but **moot until the mount bug is fixed** — at which point it must be re-checked (see §5).

### RC-B — Album container card has no aspect-ratio rule → collapses to a 1px sliver ❌

**Symptom:** the single album card (idx 63) renders as a **55px-tall** strip: its `.hr-card-video-vis` is **1px tall**, so the album cover is invisible; only the title + "15 tracks" + badge show. This is the 55px row track at the bottom of the grid.

**Mechanism:** `AlbumCard` (JSX L1372–1397) is structurally identical to `GalleryCard` — it sets only `backgroundImage` inline and relies on CSS for the box's aspect-ratio. CSS gives the gallery one — `.hr-card-gallery .hr-card-video-vis { aspect-ratio: 4/5; flex:none; }` (L1189) — but **there is no `.hr-card-album .hr-card-video-vis` aspect-ratio rule anywhere** (the album CSS block, L1388+, styles only the badge and the overlay). With no aspect-ratio and `flex` not pinned, the box has no height to derive and collapses. One missing CSS line.

### RC-C — Row-based grid + 5×-varying card heights → empty gutters ⚠️ (18 cards, plus it makes "clean" rows look uneven)

**Symptom:** short cards stretched far past their content, leaving large empty background below the foot. Examples: YouTube idx 60 — a 16/9 thumbnail (vis 322px) sitting in a **769px** tile (≈390px empty) because it shares a row with the 715px-tall gallery cover; link idx 16 — a 16/9 thumb (vis 156px) in a **786px** tile (≈600px empty) because its row contains the Instagram photo; every span-1 YouTube thumb (vis 156px) in a 400px row (~165px empty) because the row's span-2 neighbours are taller.

**Mechanism:** §1. `align-items: stretch` (default) + `grid-auto-rows: auto` means row height = tallest member and shorter members inflate. The inputs that make rows tall and uneven are themselves **by design** — random spans (RC-D) and the locked per-type aspect ratios (16/9 vs 4/5 vs 9/16). A **row** grid is the wrong layout primitive for content of intentionally varied height; it turns variety into gutters. (`grid-auto-flow: dense` only back-fills horizontal gaps; it does not equalize heights.)

### RC-D — Context, NOT a defect: the size variety is operator-locked

Random column spans (`pickSpan`) and per-type aspect ratios are the **intended** "varied sizes" aesthetic locked 2026-05-22. **Do not "fix" the variation** — mixed widths and mixed heights are wanted. The fix target is only that the current layout renders that variation as gutters instead of a clean masonry. (Also minor, likely intentional: 4 fixed 280px columns + `justify-content:start` leaves ~660px of empty space on the right at 1920px width. Flagged, not classified as a defect.)

## 4. Separating broken from correct-by-design

| Observation | Verdict |
|---|---|
| YouTube cards open out / show only a thumbnail in the grid | **Correct-by-design.** LinkCard thumbnail tile; the in-site YouTube lightbox is a planned build, not a grid-shape defect. Thumbnails render at the locked 16/9. |
| ReverbNation / ticketing cards (the 6 `link` tiles) link out | **Correct-by-design.** Per `RN_ARCHIVED_PAGE_CARDS...` these are archival provenance link-outs; the real RWTH audio is already in-site via the album overlay. Their *content* (thumbnail) is fine — only their **gutter** is a defect (RC-C). |
| Mixed card widths (some 1-col, some 2-col) | **Correct-by-design** (`pickSpan`, operator-locked). Not a bug. |
| Mixed aspect ratios per type (16/9 vs 4/5 vs 9/16) | **Correct-by-design** (locked per-media-type aspect). Not a bug. |
| 16 Facebook boxes show nothing | **Defect (RC-A).** The embed is *meant* to render inline; it never mounts. |
| Album tile is a 55px sliver | **Defect (RC-B).** Missing CSS rule. |
| Empty gutters under stretched cards | **Defect (RC-C).** Layout primitive, not the content. |

## 5. Fix plan — sized & sequenced per root cause

Ordered by value × safety. All three are **front-end only** (no MV write, no export change).

**Fix 1 — Album aspect-ratio (RC-B). Size: XS (1 CSS line). Risk: none.**
Add, next to the gallery rule (CSS ~L1189):
`.hr-card-album .hr-card-video-vis { aspect-ratio: 1 / 1; flex: none; }`
(Album art is square; use `4 / 5` instead if matching the gallery tile is preferred.) Fixes idx 63 immediately. Verify the 55px row track grows and the cover shows.

**Fix 2 — Facebook embed mount + fallback (RC-A). Size: S–M. Risk: Med (FB render variance).**
Two parts:
1. *Make the width reliable.* In `useElementWidth` (JSX L1148), seed the width synchronously before paint — e.g. set initial state from `ref.current.getBoundingClientRect().width` in a `useLayoutEffect`, and/or stop discarding the first reading. Alternatively, drop the JS width dependency entirely: render the iframe at `width:100%` inside the CSS aspect-ratio box and remove the `tileW>0` gate (the box already has a per-kind shape). This alone re-mounts all 16 embeds.
2. *Add a static preview fallback* so a slow/refused/login-walled embed degrades to an image + title (scoping doc §4.3 Option A static tile) instead of a blank box — because a cross-origin iframe gives no load/error signal.
**Required follow-up:** once mounting works, re-verify in a **logged-out / incognito** window (scoping doc §6.2) — the operator's logged-in view will over-represent what a public visitor sees. I did **not** run an incognito pass this session because the current defect is upstream of FB auth (nothing mounts either way); it becomes meaningful only after part 1 lands. Happy to run it then.

**Fix 3 — Kill the gutters / true masonry (RC-C). Size: M. Risk: Low–Med.**
The variation is wanted; the row-stretch is not. Options, honestly bounded:
- **(a) Interim, cheap, low-risk:** set `align-items: start` on `.hr-artifact-grid`. Stretched cards collapse to content height, so the empty space leaves the *card* (no more "tall empty tile") — though uneven *row gaps* remain. Immediate visual improvement, ~1 line.
- **(b) Real fix — JS masonry:** measure each card and column-pack (or a masonry lib). Honors the locked 1-/2-col spans and removes gutters. More code, but the correct systematic answer.
- **(c) Native CSS masonry (`grid-template-rows: masonry`)** — cleanest in principle but still experimental / limited browser support; not production-safe yet.
- **Avoid CSS multicol (`column-count`)** — it cannot express the 2-column span feature, so it would break the locked design.
**Recommendation:** ship (a) now as a quick win; pursue (b) for the durable fix. Re-check that tall drivers (photo idx 14, gallery idx 62, reels idx 15/21) still look intentional under masonry.

**Suggested sequence:** Fix 1 (instant) → Fix 2 part 1 (16 boxes light up) → Fix 3a (gutters shrink) → Fix 2 part 2 + incognito verify → Fix 3b (masonry). After each, re-run this measurement pass to confirm row tracks tighten toward content height.

## 6. Method & caveats (honesty)

- Measured live DOM via `getBoundingClientRect` + `getComputedStyle` on all 64 `.hr-card` nodes; scrolled the real container (`.wb-scroll.hr-panel-scroll`, 11.7k px) fully before asserting "no iframe," so empty FB boxes are not a lazy-load false-negative.
- All four mechanisms were cross-checked against host-intact source (`HrExhibitFlow.jsx` / `.css`) via the Read tool, not inferred from rendering alone.
- **Not done:** per-thumbnail image-load verification — YouTube/link thumbnails are CSS `background-image`s, which expose no load signal; the code has a `useResolvedThumb` maxres→hq fallback, but a broken individual thumbnail would not be caught by this geometric pass. If the operator suspects specific dead thumbnails, that's a separate per-URL check.
- **Not done:** logged-out/incognito Facebook pass — moot under the current RC-A mount failure (see Fix 2); will matter after.
- Measured at one viewport (1920×869). Spans are id-deterministic (stable across reloads), but row composition — and therefore which cards get gutters — shifts with viewport width and with deck filtering. The *classes* of defect (RC-A/B/C) are viewport-independent; the exact per-card gutter sizes are not.
